# 仕様: ログイン方式（ID/PW・商談用アクセス）

初版 2026-08-06。所管は accounts アプリだが、管理UIは `/service_admin/`（home アプリ）にある。
画面側の仕様は [Home_SPEC.md](Home_SPEC.md) を参照。

## 1. 全体像

ログイン経路は2つ。どちらも**パスワード入力が必須**で、失敗回数のロックを共有している。

| 経路 | 用途 | URL |
|---|---|---|
| ID/PW | 管理者・既存ユーザー | `/accounts/login/` |
| 商談用アクセス | 商談ごとに発行する一時アクセス | `/guest/<token>/` → `/guest/` |

商談用URLは相手に渡すものなので短く保つ（例: `https://example.com/guest/<15桁のトークン>/`）。

商談用アクセスのトークンは「**どのアカウントか**」を指すだけで、それ単体ではログインできない。
リンクが漏れてもパスワードが無ければ入れない、という構造を崩さないことがこの設計の前提。

## 2. ID/PWログイン（`LockedLoginView`）

Django標準 `LoginView` のサブクラス。画面・フォームは標準のまま。

- POST時にまずロック状態を確認し、ロック中は**パスワードの照合を行わない**
  （照合させると総当たりの速度を落とせないため）。メッセージを出してログイン画面へ戻す
- 失敗時は `register_failure`、成功時は `register_success`
- 累計が失効閾値に達しても**アカウントは無効化しない**。締め出しを避けるためERRORログのみ出す

## 3. 商談用アクセス

### 3.1 ライフサイクル

```
発行（/service_admin/）
  ├ 対象ユーザーは「新規作成」または既存から選択（新規なら同時に作成）
  ├ トークン15桁を生成 → ハッシュのみDB保存
  ├ パスワード16桁を自動生成 → User に set_password
  └ URLとパスワードを画面表示（「閉じる」まで表示。DBには平文を持たない）
        ↓  URLとパスワードは別経路で相手へ渡す
着地（GET /guest/<token>/）
  ├ ハッシュ照合・期限・失効を確認
  ├ セッションへ id を保存
  └ 302 → /guest/            ← URLからトークンが消える
パスワード入力（GET/POST /guest/）
  ├ 成功 → login() → /home/、last_accessed_at 更新、履歴に経路を記録
  └ 失敗 → カウント。閾値でロック、累計超過で失効
終了
  └ 手動失効 / 絶対期限 / 無操作期限 のいずれか
```

### 3.2 トークンの扱い

- 生成: `secrets.choice` による15桁（英小文字＋数字）。約77bit相当。
  URLの短さを優先しているが、総当たりはロック（連続5回で指数バックオフ）と
  失効（累計20回）で抑えるため、推測は現実的でない
- 保存: `salted_hmac('accounts.MeetingAccess.token', raw)` のハッシュのみ。
  生の値はDBに残らない。総当たりの余地が無いため低速ハッシュは使わず、インデックス検索できる形にしている
- 着地後はセッションへ移し、302でURLから消す。ブラウザ履歴・Referer・アクセスログに残る窓を最小化する
- 無効なトークンは**理由を区別せず**同じ404ページを返す（探索の手がかりを与えない）
- レスポンスに `Referrer-Policy: same-origin` / `X-Robots-Tag: noindex, nofollow` / `no-store` を付与
  - **`no-referrer` は使わない**。Chrome がそのページからのフォーム送信で `Origin: null` を
    送るようになり、DjangoのCSRF検証（Origin照合）が必ず失敗する。
    `same-origin` でも外部（CDN等）へは Referer を一切送らないため、目的は達成できる

### 3.3 パスワード

- 発行時に自動生成する（16桁）。人には決めさせない
- 文字集合から `0 O o 1 l I` を除外（口頭伝達・スマホ入力での誤りを避ける）
- 「パスワード再生成」を外して発行することもできる（既存パスワードを変えない）。
  同じユーザーに複数のトークンを紐づける場合に使う
- **トークン経由でパスワード変更・再設定はさせない**。これを許すとリンク単体が鍵になる

### 3.4 失効条件

| 条件 | 状態表示 | 判定 |
|---|---|---|
| 手動失効 | 失効（手動失効） | 管理画面の「失効」ボタン |
| 失敗回数超過 | 失効（失敗回数超過） | 累計失敗が `MEETING_REVOKE_THRESHOLD` に到達 |
| 絶対期限 | 期限切れ | `expires_at` を経過（発行時に `MEETING_EXPIRE_DAYS` から算出） |
| 無操作期限 | 無操作期限切れ | 最終アクセス（無ければ発行日時）から `MEETING_IDLE_DAYS` 経過 |

失効・期限切れのトークンは着地の時点で弾かれる。ログイン済みセッションは即座には切れない
（セッション自体の期限は `SESSION_COOKIE_AGE`＝6時間）。

## 4. 失敗ロック（`accounts/lockout.py`）

両経路が同じロジックを共有する。カウンタは `LoginLockout` テーブル（キャッシュではなくDB）。

```
連続失敗 1..4 回   → ロックなし
連続失敗 5 回      → 60秒ロック
連続失敗 6 回      → 120秒
連続失敗 7 回      → 240秒 …（LOGIN_LOCK_MAX_SECONDS で頭打ち）
累計 20 回         → 商談用アクセスは失効／ID/PWはERRORログのみ
```

- **時間窓を持たない**。カウンタが戻るのは**ログイン成功時のみ**。
  短い時間窓（例: 30秒）で自然回復させると、窓の直前で止める総当たりを素通しするため
- ロックキー
  - ID/PW: `user:<username>@<ip>`（既定）または `user:<username>`（`LOGIN_LOCK_SCOPE=user`）
    - 既定でIPを含めるのは、第三者がわざと失敗させて管理者を締め出す自DoSを避けるため
    - 分散攻撃を重く見る場合は `user` に切り替える
  - 商談用: `meeting:<id>`（IPで分けない。失効させること自体が目的のため）
- カウンタをDBに置いているのは、`CACHES` 未定義＝LocMemCache だとワーカーごとに分かれて数え漏れるため

## 5. 設定（`.env`）

未設定でも既定値で動作する。定義は `config/settings.py`。

| キー | 既定 | 意味 |
|---|---|---|
| `LOGIN_LOCK_THRESHOLD` | 5 | 連続何回の失敗でロックするか |
| `LOGIN_LOCK_SECONDS` | 60 | 最初のロック秒数（以降倍化） |
| `LOGIN_LOCK_MAX_SECONDS` | 3600 | 倍化の上限秒数 |
| `LOGIN_LOCK_SCOPE` | `user_ip` | ロックの単位（`user_ip` / `user`） |
| `MEETING_REVOKE_THRESHOLD` | 20 | 累計失敗で商談用トークンを失効させる回数 |
| `MEETING_EXPIRE_DAYS` | 30 | 発行時の既定有効日数（上限も兼ねる） |
| `MEETING_IDLE_DAYS` | 7 | 無操作期限。0で無効 |
| `MEETING_TOKEN_LENGTH` | 15 | URLに載るトークン桁数 |
| `MEETING_PASSWORD_LENGTH` | 16 | 自動生成パスワード桁数 |

## 6. データモデル

### `MeetingAccess`（商談用アクセス）

| フィールド | 内容 |
|---|---|
| `label` | 商談名・相手先 |
| `user` | 紐づくDjangoユーザー |
| `issuer` | 発行者（削除時はNULL） |
| `token_hash` | トークンのHMACハッシュ（unique） |
| `issued_at` / `expires_at` / `last_accessed_at` | 発行・期限・最終アクセス |
| `revoked_at` / `revoked_reason` | 失効日時と理由（`manual` / `lockout`） |
| `note` | メモ |

### `LoginLockout`（失敗カウンタ）

`key`（unique） / `fail_count`（連続） / `fail_total`（累計） / `locked_until` / `last_failed_at` / `last_ip`

### `LoginHistory` への追加

`meeting_access`（NULL可）。商談用トークン経由のログインならその発行分を指す。
ID/PWログインではNULL。サービス管理画面のアクセスログで「経路」として表示する。

## 7. 運用手順

1. `/service_admin/` の「新規発行」で、商談名・対象ユーザー・有効日数を指定して発行
   - 対象ユーザーの既定は「＋ 新規作成」。ユーザー名を入れれば作成と発行が同時に行われる
   - 既存ユーザーを選んだ場合は「パスワード再生成」の有無を選べる
2. 表示されたURLとパスワードを**別々の経路**で相手に渡す（コピーボタンあり）
3. 控え終わったら「閉じる」を押す。閉じると再表示できない
4. 送り直したい・控え損ねた場合は一覧の「再発行」（新しいURL・パスワードを作り、元は失効）
5. 商談の成否が決まったら「失効」ボタンで打ち切る
6. 失効し忘れても、絶対期限（30日）と無操作期限（7日）で自動的に使えなくなる

## 8. 発行内容の再確認について

URLとパスワードは**発行時にしか表示できない**。DBにはトークンのHMACハッシュと
パスワードハッシュしか持たないため、後から平文を復元する手段が無い（意図的な設計）。

運用上の救済として次の2つを用意している。

- 発行結果パネルは「閉じる」を押すまで残る（画面を離れても消えない）
- 一覧の「再発行」で、同じ商談名・ユーザーのまま新しいURLとパスワードを作り直す
  （元のトークンは同時に失効し、相手の旧リンクは使えなくなる）

平文をそのまま再表示できるようにするには、URLとパスワードを復元可能な形でDBに
保存することになる。その場合、DBが漏れた時点でアカウントがそのまま乗っ取られる
（現状はハッシュのみなので漏れても直ちには使えない）。この差を受け入れられる場合のみ
検討する。

## 9. 既知の制約・今後

- 1つの商談用アクセスを複数人で共有すると、誰がアクセスしたかは特定できない。
  個人を追う必要があるなら1人1トークンで発行する
- 商談用ユーザーもログイン後は `/accounts/password_change/` でパスワードを変更できる
  （トークン経由ではないので許容している）
- 期限切れレコードを定期削除するコマンドは未作成（`prune_login_history` と同じ形で追加できる）
- ロックの解除は時間経過のみ。管理画面からの手動解除は未実装
